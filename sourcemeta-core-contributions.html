Sourcemeta Core

From Terminal Colors to Protocol Contracts

What 24 merged pull requests in Sourcemeta Core taught me about systems engineering

Harsh Popat · November 2026

My first contributions to Sourcemeta Core dealt with a question I could see on screen: when should a command print color? A few weeks later I was looking at a stream of four integers and asking why only three reached a callback. Both came down to an assumption at an interface. Captured output can still need color, and copying an input iterator can leave both copies attached to the same stream.

Across 24 merged pull requests, I worked on terminal output, JSON and OpenAPI, cryptography, benchmarking, and the Model Context Protocol (MCP). The most useful part of the work was learning to describe exactly what each change guarantees, how I could demonstrate it, and where its guarantee ends.

Start with a boundary you can see

I started by adding ANSI styling primitives to Core. The library can style interactive terminal output and suppress escape sequences when the destination is redirected. Then I added an explicit policy for callers that want color even in captured output. The caller chooses the rendering policy independently of the destination. Captured subprocess tests make the distinction concrete by comparing exact bytes under each mode. #2790 #2808

Unified diffs raised a related design question. A CLI might want additions in green and deletions in red, while another consumer might need plain patch output. I added a callback that receives the type, prefix, and content of each line. Core keeps control of the diff structure and line endings, and the caller chooses how the line looks. #2871

That separation became a useful pattern for the rest of the work. The library owns a contract that other programs can rely on. Consumers get an explicit way to make the choices that belong to them.

Where the input contract matters

Four integers in, three callbacks out

With two workers, I could feed 1 2 3 4 into parallel_for_each through a C++ stream iterator and get callbacks for only 1 3 4. The helper copied an iterator to look ahead, but both copies were tied to the same underlying stream. Advancing the copy consumed input. Queueing iterator copies for later work relied on the same multipass assumption.

The fix was to process single-pass inputs in order on the calling thread and report an effective parallelism of one. Forward iterators still use the worker path. The tests check that every stream value arrives exactly once, and a forward-iterator control checks that callbacks still run on workers. #3054

What a failure leaves behind

For a memory-mapped binary read, a length of SIZE_MAX could make the output string throw a length error before the reader checked how many bytes remained. I moved that bounds check ahead of the resize. The regression checks both the error type and the reader’s position afterward. If the caller handles the error, the bytes that were available before the failed read are still available. #3055

A JWT audience check had a different ordering problem. A correctly signed token could carry an audience array with a matching string and a number. The verifier accepted the match even though the array violated the claim’s required shape. Checking every member before accepting the match makes ["client", 42] and [42, "client"] fail consistently. I tested both orders through the audience helper and the signed-token verification path. #3053

The OpenAPI case led to a different outcome. I built a small multi-document fixture for a discriminator mapping whose anchor is discovered later in the bundle. The target resolved consistently before and after bundling, so the merged PR adds coverage without changing the bundler. That fixture exercises a branch the original bundle suite hadn’t reached in my coverage run. #3075

Measure the operation that changed

From allocator questions to stream writes

I added benchmarks for KrakenD parsing and pretty-printing and for compact serialization of an ISO-language schema. Keeping file loading outside the timed loops lets each benchmark focus on a specific workload. Later, I added --repeat so the runner could execute a chosen number of one-iteration runs without adaptive calibration, making external profiling captures easier to compare. #2898 #3045

Compact serialization offered a way to isolate a smaller cost. The existing writer already emitted contiguous unescaped characters in runs. I added a path that emits a short unescaped string and both of its quotes in one stream write. In the paired Linux measurements reported on the PR, wall time fell by 11.6% to 27.7% across two fixtures, two allocator configurations, and two output modes. Allocation counts were unchanged. The improvement also showed up when I reused the stream and borrowed its output view. #3057

The first version slowed down an escape-heavy synthetic case. It scanned the same prefix twice when the escape was near the end of a short string. I passed the first escape position to the existing writer so it could resume there. That case mattered because it forced me to measure the fallback alongside the fast path. #3057

A portable crypto result has a portable-crypto scope

In the AES-GCM reference backend, I worked on GHASH, which combines blocks using multiplication over a binary finite field. The implementation replaced byte-oriented operations with two 64-bit words and mask-based XOR and reduction. The PR also simplified multiplication by fixed AES coefficients. The reported median for the local GHASH microbenchmark went from about 1.07 microseconds to 223 nanoseconds. The reference-backend test runs included standard vector suites. That result describes this backend and benchmark setup. #2905

These changes gave me a rule for writing performance claims. Name the operation, the fixture, the build, and the statistic. If I can’t say where the number came from, it doesn’t belong in the headline.

What Core guarantees in MCP

The largest contribution added MCP 2026-07-28 support to Core’s reusable helpers, alongside revision-aware behavior for three 2025 revisions. I separated the JSON-RPC notification constructor, the MCP header split, and the test-file reorganization into smaller changes. That let each prerequisite be reviewed independently of the protocol feature. #2954 #2958 #2961 #2878

The follow-ups concentrated on concrete edges. Numeric fields that require integers should judge mathematical value, so an integer-valued representation such as 1.0 can be accepted where the relevant field rules allow it. Empty metadata keys fail validation. Tests cover version gates, header value round trips, and continuation behavior. Smaller improvements removed copies, made ignored results easier for the compiler to flag, and gave callers an option to move a JSON payload into a result writer. #3003 #3023 #3037 #3024 #3025

I also added helper benchmarks before changing parameter-header lookup. The 64-descriptor benchmark improved from 53.70 to 15.95 microseconds in the comparison reported on the PR. The unchanged subscription benchmark varied by about 16% on the same host. I can say the header fixture improved in that run and still leave room for a different result under other conditions. #3031 #3032

Two documentation-and-test PRs captured where the application takes over. Building a successful MCP envelope leaves application schema validation to the caller. Checking an echoed continuation token leaves expiry, authorization, and single-use state consumption to the deployment. One test calls continuation validation twice with the same expected token to make that boundary explicit. #3043 #3044

The 24 PRs cover very different code, but the part I want to keep doing is the same. Take an assumption somebody could get wrong, find an input that makes it visible, and leave a test or a measurement that the next contributor can use. That can be as small as captured ANSI bytes, or as consequential as a malformed claim in a signed token.
